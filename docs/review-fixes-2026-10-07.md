## 1. Отличать сборку нового импорта от старой сборки

**Где:** `src/ui/siteCommands.ts`, функция `isBuildOf`, строки 94–98 на проверенном коммите.
Связанные файлы: `src/ui/siteWorkerController.ts`, `src/ui/sitePipeline.ts`.

### Ошибка

`isBuildOf` сравнивает только количество и ID групп. При каждом импорте группы снова получают
ID `g1`, `g2` и далее. Поэтому предыдущая сборка с тем же количеством групп может быть принята
за готовую сборку нового шаблона, даже если механизмы, координаты или связи отличаются.

`whenBuilt` завершается раньше времени. Автоматическая оптимизация может отменить текущую
сборку нового импорта, и новый шаблон не будет показан до завершения оптимизации.

### Воспроизведение

1. Подготовить новый шаблон с группами `g1` и `g2` — electric blast furnace.
2. Оставить в хранилище результатов предыдущую готовую сборку с теми же ID, но с vacuum freezer.
3. Вызвать `whenBuilt` для нового шаблона.
4. Сейчас функция сразу возвращает `true`, хотя новый шаблон ещё не собран.

### Что поправить

- Передавать вместе с результатом сборки идентификатор задания или версию исходного шаблона.
- Проверять принадлежность результата именно ожидаемому импорту, а также завершение сборки.
- Не опираться только на ID групп: они переиспользуются, а данные worker проходят клонирование.
- Связывать ошибки сборки с конкретным заданием, чтобы устаревшая ошибка не отменяла ожидание
  нового импорта.
- Сохранить отмену автоматической оптимизации при редактировании или замене шаблона пользователем.

### Критерии приёмки

- [ ] Unit-тест: старая сборка с теми же ID не завершает ожидание нового импорта.
- [ ] Unit-тест: промежуточная сборка без законченной трассировки не завершает ожидание.
- [ ] Unit-тест: готовый результат нужного задания завершает ожидание.
- [ ] Unit-тест: редактирование, замена шаблона, ошибка его сборки и таймаут отменяют ожидание.
- [ ] E2E-тест: повторный импорт с тем же количеством групп сначала показывает новый обычный
      шаблон, затем запускает его оптимизацию.

## 2. Включить калибровку температуры в бюджет времени

**Где:** `src/model/site/anneal.ts`, калибровка в строках 585–597 и начало таймера в строке 604
на проверенном коммите. Связанный файл: `src/model/site/optimize.ts`.

### Ошибка

Таймер основного цикла начинается после калибровки температуры. Калибровка вызывает оценку
до 12 раз при использовании реального router, но её время не расходует переданный бюджет.
Основной цикл затем получает весь выделенный ему бюджет заново.

В детерминированном тесте с модельной стоимостью каждой трассировки **400 мс** оптимизация
при бюджете **10 000 мс** использовала **14 400 мс**. Это превышает заявленный допуск в одну
трассировку: **10 400 мс**. Эти числа получены на внедрённых модельных часах, а не замером
производительности браузера.

### Воспроизведение

1. Подготовить валидный шаблон из двух связанных групп с достаточным свободным местом.
2. Использовать builder, который при каждой трассировке прибавляет к модельным часам 400 мс.
3. Запустить `optimizeSite` с `reshape: false`, `seeds: 1`, `iterations: 0`,
   `refineSteps: 500`, `refineRuns: 1`, `budgetMs: 10000` и внедрённой функцией `now`.
4. Сейчас суммарное время модельных часов составляет 14 400 мс.

### Что поправить

- Начинать отсчёт до дорогих оценок и калибровки температуры.
- Проверять оставшееся время внутри калибровки и основного цикла.
- Учитывать уже потраченное время при переходе между этапами `optimizeSite`.
- При исчерпании бюджета возвращать лучший найденный допустимый вариант.
- Сохранить детерминированность при фиксированных seed, числе итераций и внедрённых часах.

### Критерии приёмки

- [ ] Unit-тест: описанное воспроизведение укладывается в бюджет с допуском одной трассировки.
- [ ] Unit-тест: калибровка прекращается, если бюджет исчерпан во время её выполнения.
- [ ] Unit-тест: при нулевом бюджете сохраняется исходный шаблон после обязательной оценки.
- [ ] Существующие проверки качества результата и детерминированности продолжают проходить.

## 3. Разрешить оптимизацию одной группы с подключёнными портами

**Где:** `src/model/site/anneal.ts`, условие выхода в строке 478 на проверенном коммите.

### Ошибка

Условие `m.n < 2` отключает поиск для одной группы. При этом у группы могут быть сети с
фиксированными входными и выходными портами, а перемещение может значительно сократить трубы.

В проверке с реальным builder оптимизатор не попробовал ни одного альтернативного варианта.
Перемещение одной группы EBF сократило трассировку с **65 до 11 блоков** при нулевом количестве
проблем и неподключённых терминалов в обоих вариантах.

### Воспроизведение

1. Создать шаблон размером `80 × 80`, коридор `2`.
2. Добавить одну группу electric blast furnace, количество `1`, поворот `0`, позиция `[30, 20]`,
   limits `{ x: null, y: 1, z: null }`.
3. Добавить два фиксированных предметных порта: вход `[0, 20]` и выход `[0, 26]`.
4. Соединить вход с группой, а группу с выходом отдельными ресурсами.
5. Запустить оптимизацию: сейчас `tried` равно `0`.
6. Для сравнения собрать тот же шаблон с группой в позиции `[3, 20]`: трассировка короче.

### Что поправить

- Разрешить поиск для одной группы при наличии сети и допустимого исходного размещения.
- Оставить для неё перемещение, поворот и изменение упаковки, если применимо.
- Ограничить операции обмена и другие операции, которым нужны две разные группы.
- Сохранить ограничения границ, коридоров, этажей и `limitsLocked`.

### Критерии приёмки

- [ ] Unit-тест с реальным builder: одна группа с портами получает альтернативные варианты.
- [ ] В приведённом сценарии результат сокращает трассировку без ухудшения соединений и предупреждений.
- [ ] Пустой шаблон обрабатывается корректно.
- [ ] Существующие тесты многогрупповых шаблонов и блокировки limits продолжают проходить.
