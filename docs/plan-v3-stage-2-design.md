# Дизайн этапа 2 — принят с уточнениями пользователя

Реализация разрешена после уточнений 9 октября 2026. Один люк обслуживает одну жидкость; ресурсы и роли приходят
из импорта или от пользователя, без поиска рецептов.

## Распределение ресурсов

`withDemand` перестаёт поднимать структурные минимумы. Пара «вид люка, ресурс,
выходной слот» становится требованием всей группы. Энергия, обслуживание, минимумы
по ролям и корпусам остаются требованиями каждого контроллера. Необязательный
`ResourceBinding.unitId` задаёт ручное назначение в инспекторе; отсутствие означает «авто».
Логические ключи назначений и индивидуальные тиры сохраняются при перемещении.

`placeResourceHatches` существующим поиском с возвратом совместно выбирает машину,
клетку, роль и тир. Сначала обязательные интерфейсы, затем непокрытые ресурсы.
Ресурсный люк может выполнить структурный минимум, поэтому лишний пустой люк не создаётся.
`missing` проверяет покрытие группы. Для С2 результат: по 3 входа, 2 выхода,
собственные энергия и обслуживание на каждой машине.

Один агент может обслуживать несколько машин: общий люк покрывает их минимумы;
при отсутствии общей клетки каждая получает собственный люк с тем же ресурсом.
`unitId` требует покрытие выбранной машиной; копии для минимумов остальных допустимы.
В инспекторе машины показываются с 1, в документе ID начинается с 0.
После уменьшения группы исчезнувший ID игнорируется с предупреждением и работает как
«авто». Он сохраняется в документе для undo/redo; при возвращении машины снова применяется.
Файлы, ссылки и localStorage сохраняют ID; старые планы без него читаются как «авто».

## Общие клетки и ёмкость

Физический люк получает все `unitIds` содержащих его структур; каждая должна принимать
его вид, роль, сторону и тир. Энергия и обслуживание крекеров неделимы.
Занятая общая клетка уменьшает счётчики корпусов каждого владельца; откат восстанавливает всех.
Экономится один физический блок, но расходуется ёмкость каждой машины.
Сумма ёмкостей — верхняя граница, не гарантия вместимости выбранной геометрии.
До поиска расклада вычисляется нижняя оценка спроса против суммарной ёмкости.
С2б отвергается сразу: 15 против 14. Для показа обязательных интерфейсов выполняется
один частичный проход; альтернативные расклады не перебираются.

## Расположения

Стопки и зазоры уже есть в `layoutCandidates`: общая грань/касание по Y,
касание/зазоры по X/Z, повороты 180°. `resolveLayout` проверяет распределение
на существующих кандидатах, упорядоченных по компактности. Существующая трассировка
и оптимизация сохраняют приоритет правил, подключённости, поверхности, поворотов и длины.
С2в сравнивает результат с независимыми допустимыми примерами; глобальный оптимум
не обещается. Поиск и трассировка ограничены бюджетами. На этапе 2 геометрические
кандидаты и механизм экономии не расширяются.
`limitsLocked` остаётся жёстким ограничением; свободные предпочтения допускают `loosened`.

Индивидуальное зеркало добавляется на этапе 3: флаг юнита учитывают геометрия,
совместимость стен, поиск клеток и кэши. Такие кандидаты входят в тот же поток
`layoutCandidates`; общая стена должна иметь совместимые типы. Для С2 уже достаточно
стопки или зазора без нового зеркала.

## Проверка после трассировки

Независимый валидатор самостоятельно восстанавливает владельцев физических клеток,
считает корпуса и минимумы каждого контроллера, проверяет окончательные стороны,
роли, тиры, покрытие группы и ручные назначения. Список «покрыто» размещателя не используется.
Сборка, «Выровнять» и «Оптимизировать» используют этот же валидатор.

Бюджеты размера не повышаются. При необходимости используется разделение кода.

Приёмка: С2/С2в/С2г проходят; С2б сохраняет ошибку; положительные/отрицательные тесты
покрытия и общих клеток; ручные назначения и тиры переживают операции с планом.
