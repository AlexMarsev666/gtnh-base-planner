# Этап 2: распределение ресурсов группы

Отчёт исходной реализации `c97d20c`. Уточнение «сначала каждой машине полный набор»
и исправление регрессии обычных групп описаны в [отчёте доработки](plan-v3-stage-2-followup.md).

Ресурс покрывается всей группой. Каждый контроллер сохраняет структурные минимумы,
допустимые роли, энергию, обслуживание и требуемые корпуса. Один люк несёт один ресурс.

## Изменения

- `resourceAllocation.ts`, `resourceRoles.ts`: отдельные требования ресурсов группы,
  автоматическое распределение с ограниченным возвратом, ручной `unitId`, проверка
  нижней оценки спроса до перебора раскладов. Для С1 — 12/7, для С2б — 15/14.
- `resourcePlacement.ts`, `group.ts`: больше нет полного набора ресурсов на каждом
  юните. Структурный минимум выбирает подходящий ресурс вместе с клеткой. Один агент
  обслуживает обе машины через общий люк или два собственных. Каждый общий люк
  расходует ёмкость и корпусные ограничения всех физических владельцев.
- Ресурсная связь сама по себе не создаёт минимум «один люк на каждой машине» для
  необязательного интерфейса. Минимумы берутся из структуры; пустые шаблоны сохраняют
  прежние значения по умолчанию.
- На раскладе, где даже структурные минимумы нельзя сопоставить допустимым клеткам,
  выполняется одна попытка назначения ресурсов, затем выбирается другая геометрия.
  Повторение заведомо бесполезных назначений устранено без увеличения таймаутов.
- Независимая проверка в `build.ts` проверяет финальное покрытие, ручные назначения,
  роли, тиры, корпуса и владельцев клеток. Ей не нужны ключи назначений размещателя.
  «Выровнять» и «Оптимизировать» используют эту же сборку и проверку.
- `GroupInspector.svelte`: выбор «Automatic / Machine N» для ресурса. Изменение роли
  сохраняет машину. Индивидуальный тир сохраняется и у повторённого ресурсного люка.

`unitId` — локальный ID, начиная с 0; в интерфейсе машины нумеруются с 1. Отсутствующее
поле означает «авто». После уменьшения группы исчезнувший ID игнорируется при
размещении с предупреждением, но сохраняется в документе для undo/redo. После
возвращения машины назначение снова применяется. Предупреждение не считается
нарушением структуры в оценке оптимизатора.

Файлы JSON, сжатые ссылки, localStorage, дублирование и undo/redo сохраняют поле.
Версия формата не менялась; старые планы читаются как «авто». Отрицательные,
дробные и другие недопустимые ID отвергаются кодеком.

## Приёмка и проверки

- С1, С2, С2б, С2в, С2г проходят. С2 и С2в сначала запускались как `it.fails`:
  Vitest сообщил неожиданный успех. После этого они стали обычными регрессиями,
  чтобы новый успех не делал CI красным.
- С2в сравнивает результат с 20 независимо найденными допустимыми трассируемыми
  примерами. Это проверка конкретного случая, а не обещание глобального оптимума.
- Положительные и отрицательные тесты проверяют общий/раздельный агент, ручную
  машину, неверный ресурс и владельцев общей клетки; отдельный тест проверяет
  повторённый ресурс питания с индивидуальным тиром. Общий агент с разными тирами
  владельцев получает отдельные люки; ключ повторённого ресурса сохраняет его
  логический номер, а не номер временного структурного слота.
- Старые тесты `build.test.ts` и `lockedFluidHatches.test.ts` обновлены под новую
  семантику: избыток ресурса проверяется через реальное размещение группы вместо
  искусственного завышения структурного минимума функцией `withDemand`.
- `npm run check`: 0 ошибок и предупреждений. `npm run build` и `npm run size`
  проходят: main **397,6/400 КБ**, worker **135,9/140 КБ**. Бюджеты не повышены.
- `npm test`: **4586/4586**, 78 файлов; `npm run e2e`: **42/42**, включая новый
  тест выбора машины. `npm run format` и `npm run format:check` выполнены успешно.
  Проверен скриншот нового инспектора: выбранная машина отображается, все 10
  подключений трассированы. Перезаписанные браузерными тестами исходные скриншоты
  восстановлены; новый снимок сохранён локально в `.tool-cache`.

Сравнение невыполнимых случаев с сохранённым исходником этапа 1 (`acd2aca`):
50 чередующихся запусков, первые 10 отброшены, медиана оставшихся 40:

| Случай |    Этап 1 |   Этап 2 |
| ------ | --------: | -------: |
| С1     |  1,798 мс | 1,210 мс |
| С2б    | 15,004 мс | 1,400 мс |

Измерения локальные; отдельный тест подтверждает, что при С2б `resolveLayout`
вообще не вызывается. Логи и временная копия исходника находятся в игнорируемой
`.tool-cache` и в коммит не входят.
