## 3. g9 и общие назначения

Исходная схема до исправления давала 37 сообщений g9. Теперь она даёт ровно одну причину:
`Machine 1: assigned 7 fluids, mandatory hatches 2, capacity 7; remove 2 assignments.`
Номер в интерфейсе начинается с 1, в файле `unitId` — с 0. Энергия и обслуживание учитываются в обязательных люках; в частичной раскладке сохраняются оба. Сообщения о неразмещённых ресурсах/минимумах, производные от доказанной перегрузки, не повторяются. Независимая физическая проверка остаётся: отрицательный тест с недопустимой клеткой по-прежнему сообщает нарушение.

Назначения `fluid:resource` (Нафта) и `fluid:light-steam-cracked-napthta` на `unitId: 1` дают ноль предупреждений g9 в полной трассировке приложенной схемы. Это отдельный положительный тест; исходный файл в docs не исправлялся молча.

В выборе машины появилась Both machines (shared hatch). `unitIds: [0, 1]` означает один физический люк в общей допустимой клетке, расходующий ёмкость каждой указанной машины. Две отдельные копии не удовлетворяют такому назначению. Выбор доступен только для люков, допускающих общее использование. Для групп большего размера выбор всех машин требует общей клетки всех выбранных машин; при её отсутствии размещение явно не выполнено.

`unitId` и отсутствие назначения читаются как раньше. Кодеки запрещают одновременные `unitId`/`unitIds`, дубликаты и некорректные массивы. При уменьшении числа машин устаревший ID сохраняется для истории, но игнорируется с предупреждением; оставшиеся существующие владельцы сохраняют требование. Если все владельцы исчезли, назначение становится автоматическим при размещении. Проверены файлы, ссылки, localStorage, дублирование, undo/redo, изменение числа машин, обе команды, роли и тиры. E2E проверяет выбор общего люка, роль и перезагрузку.

## 4. Детерминизм

Arrange использует канонические повороты и исходные пользовательские параметры упаковки. При изменении упаковки команды сохраняют их в необязательном `arrangeLimits`; ручная правка limits сбрасывает эту память. Старые файлы используют имеющиеся limits. Повторный Arrange идемпотентен; реальный тест проверяет три цикла Optimize → Arrange и восстановление после записи файла.

Optimize использует фиксированное число итераций: четыре дешёвых прогона, затем фиксированные два уточнения по 24 итерации; прогресс и температура зависят от итераций. Пользователь видит Optimization seed, значение сохраняется в плане (старые планы: 0). При одинаковых данных, зерне и параметрах завершённый поиск даёт одинаковый результат, включая разную скорость часов в тесте.

Прежний предел 10 секунд остаётся защитой. Если он прерывает поиск, частичный победитель не применяется: показывается причина, исходный план остаётся прежним. Это предотвращает применение результата, зависящего от быстродействия компьютера. Завершённый результат сравнивается с полностью трассированным исходным планом, включая нарушения и подключённость; при отсутствии строгого улучшения документ и undo-история не меняются, сообщение содержит No improvements. Повторный запуск не ухудшает оценку.

Если канонический Arrange создаёт нарушение, обе команды сохраняют исходный план с объяснением. Optimize в таком случае не запускает поиск от произвольного положения; ограничение документировано. Для исходного плана с уже существующей коллизией добавлена проверка перед применением улучшения: оно не должно делать повторный канонический Arrange небезопасным. Отдельный тест сначала воспроизвёл разные координаты следующего Arrange, затем прошёл после исправления. Положительные и отрицательные регрессии проверяют одинаковый seed, зависимость от часов, отсутствие улучшения, прерывание поиска, исходные limits и реальные повторные команды.

## 5. Эталонные метрики и видимость

Базовые значения получены настоящим builder из изолированного снимка `d2de3e27...`, а не рассчитаны по новой реализации. Пять JSON baseline-файлов содержат хэш, название и явный допуск **0**. Тест запускает текущий builder с pipes/cables/below и проверяет каждую метрику отдельно: не выше baseline.

Эталон №1 для функциональной трассировки — приложенная схема после только двух согласованных назначений g9. Её режим остаётся прежним Compact. Исходная перегруженная схема проверяется отдельно в диагностических тестах; неполное размещение ресурсов не используется как образец качества. Остальные четыре плана используют Underground trunks, глубину 3, и сохранены отдельными открываемыми JSON.

Поворот — изменение направления последовательных шагов пути. Поверхностные блоки — уникальные клетки всех путей с y ≥ 0, включая их концы. Длина — физические pipeBlocks + cableBlocks из статистики builder. Размер — ширина и глубина плана; неподключённость — terminals − connected. Все пять планов имеют ноль структурных/ролевых предупреждений. Сравнение фиксирует сырую трассировку эталонов: улучшение рядов и магистралей из шага 3 этапа 5 пока не реализуется.

E2E использует исходную схему: старый режим и подсказка видны, новый режим/глубина/зерно сохраняются после перезагрузки; роли, назначения, тиры, количества и limits не меняются. Настройки и реальный подземный просмотр зафиксированы на скриншоте после окончания сборки. Кнопки, совмещающей Arrange с аккуратной трассировкой, нет.
